# DC-000 — Plantilla de contrato de componente

`design`, subtipo **componente**. Rellenar y renombrar a `DC-<SLUG>.md`.

**Dónde vive** (§12): nace en el repo que lo necesita primero
(`.ai-dlc/design/` o junto a la spec) y promociona a `.org/contracts/design/`
cuando aparece el **segundo consumidor real** — nunca antes.

**Extensión: objetivo 80-150 líneas, límite duro 200** (el de §9). Si lo supera, hay documentación mezclada
con contrato — separarla (prueba ácida de `CONTRACT-000` §1).

## 1bis. Modo perfil de adopción *(sólo si el componente es de terceros)*

`N/A` si el componente es propio. Si es de una librería externa, **esta
sección reemplaza a las §3-§8**: no se re-especifica al proveedor.

**Procedencia** *(no normativa, no lleva ID)*: proveedor y versión —
p. ej. `PrimeReact DataTable v17`— y la URL de su documentación, que es
la fuente y **no** se copia aquí.

Cada regla del perfil lleva identificador propio, prefijo `P`, porque
se cita desde una `R*.*`, un test o un bug igual que cualquier otro
elemento normativo:

| ID | Regla | Detalle |
|---|---|---|
| P1 | variante permitida | |
| P2 | prohibido | *(combinación que este repo no admite, con motivo)* |
| P3 | token enlazado | *(propiedad del proveedor → token del `DS-*`, o valor)* |
| P4 | desviación | *(qué se hizo distinto del proveedor y por qué)* |

**Extensión de un perfil: 10-30 líneas de tabla `P*`** — el conteo es
de reglas, no del archivo: el frontmatter y los encabezados no cuentan.
El objetivo de 80-150 aplica a un `DC-*` de componente propio. Un
perfil largo es un proveedor re-especificado: cinco mil líneas
describiendo un botón que ya está implementado y documentado por quien
lo hizo (§16 *anti-patrones de brownfield*).

**En modo perfil, los criterios de aceptación de §9 se reemplazan por
éstos** — los de fábrica citan §5-§8, que este modo no usa:

| ID | Criterio | Cómo se verifica | Nivel |
|---|---|---|---|
| AC-P1 | No se usa ninguna variante fuera de las `P*` permitidas | lint / revisión de diff | automático |
| AC-P2 | Ninguna prohibición `P*` aparece en el código | lint | automático |
| AC-P3 | Las propiedades enlazadas salen del token declarado, no de un valor suelto | lint | automático |

## 5. Estados

Obligatorio enumerar **todos** los estados posibles. Un estado no declarado es
un gap de contrato (bug Tipo B), no una decisión libre del implementador.

| ID | Dimensión | Estado | Disparador | Comportamiento observable |
|---|---|---|---|---|
| E1 | interacción | reposo | | |
| E2 | interacción | foco | | |
| E3 | interacción | ocupado / en proceso | | acción bloqueada; el usuario percibe progreso |
| E4 | editabilidad | deshabilitado | | motivo comunicado, no sólo apagado |
| E5 | validez | error | | |

**Combinaciones legales** *(obligatorio)*:
`N/A — todos los estados son excluyentes` si el componente sólo puede estar en
uno a la vez, que es el caso de la mayoría. Si no, declarar qué se combina y
qué se excluye.

> **Por qué la columna `Dimensión`.** Un botón está en reposo **o** con foco
> **o** cargando: una lista basta. Un campo está *con valor, requerido, en
> error y con foco* **a la vez** — sus estados son dimensiones ortogonales
> (interacción, contenido, editabilidad, validez, obligación), no valores de
> un mismo enum. Enumerarlos en fila sin decir cuáles conviven deja al
> implementador adivinando, y una **combinación** no declarada es tan gap de
> contrato como un estado no declarado. Lo encontró la destilación de
> `COMP-002_Input` (`examples/destilacion-dc/`).
>
> El componente simple no paga por esto: escribe `interacción` en las cinco
> filas y `N/A` en la línea de combinaciones.

## 7. Tokens enlazados

Referencia a `DS-*` por `id`. **No repetir valores aquí** — duplicar es drift.

| Propiedad | Token (`DS-*`) o valor |
|---|---|
| color de fondo, variante primaria | `color.action.primary.background` |
| espaciado interno | `space.compact` |

> El `DS-*` referenciado debe declarar **intención**, no sólo valor —
> `intent`, `useFor`, `avoidFor`— y usar el formato del **W3C Design Tokens
> Community Group** como artefacto máquina. Un token sin `avoidFor` no impide
> el mal uso, que es justamente lo que un agente necesita saber.

## Nota sobre documentación previa

Es habitual llegar aquí con fichas de componente de miles de líneas. Destiladas
a esta plantilla caben en ~120 líneas más el JSON. **La diferencia no se
pierde**: es documentación (propósito, contexto, beneficios, audiencia, buenas
prácticas), y puede conservarse **sin versionarse como norma** — o generarse
desde el artefacto máquina, que es lo natural en un ciclo asistido por IA.

Destilar **un** componente real antes de escribir el resto es la verificación
más barata del modelo: si no se puede, el problema es el modelo y conviene
saberlo antes de escribir el segundo.
